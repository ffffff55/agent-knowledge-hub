# Code standards

这些规则来自审查和复盘里反复出现的要求。审查时逐条核对，哪一条没达到，就在 PR 里写明是哪一条。

子系统怎么描述和审查，见 [subsystem references](subsystems/README.md)。

## 变更本身

| 规则 | 审查时看什么 |
| --- | --- |
| 一次变更只做它的目标需要的事 | 每个行为变化都有理由。无关重构、额外功能和产品决策改动，另开 PR。 |
| 修复覆盖它声称要修的全部情况 | 哪些案例变了、哪些相邻案例不变，写清楚。不同错误不要当成同一种处理。 |
| 变更在整条链路上成立 | 从用户输入跟到最终结果，包括调用方、状态和副作用。一个函数对了不等于整件事对了。 |
| 同类 bug 一起修掉 | 用搜索把同一模式找全：同类 agent、子命令、守卫、调用点，都在同一次变更里修。 |
| 改了公式、列表或时序，就要重验所有建立在上面的东西 | 找出每个调用方、缓存副本和测试，跑一遍。 |
| 读取、解析或哈希失败表示「未知」 | 绝不表示「空」「没有」或「相等」。读失败的访问控制名单要失败关闭。 |
| 不要用默认值覆盖用户已经设定的值 | 写入前先列出所有读取路径，并用「用户已有自定义值」的用例测试。 |
| 不要推翻已经拍板的产品决定 | 滚动、光标、组件选型这类决定，只有维护者能改。命中就留给维护者。 |

## 测试

| 规则 | 审查时看什么 |
| --- | --- |
| 修复必须带一个去掉它就会红的测试 | 审查时把旧代码放回去跑新测试，必须真正 `FAIL`，并指出是哪个行为错了。编译失败或测试被跳过都不算。 |
| 测试不碰真实网络和真实机器配置 | 外部接口用夹具。不要读写真实的用户配置目录。 |
| 测试检验行为，不检验实现细节 | 断言用户或调用方需要的结果。 |
| main 上红掉的测试就是现在要修的 bug | 「在 origin/main 上也红」不是基线。先修或单独开 issue 写明原因，再往上堆新变更。 |
| 测试启动的东西，测试结束时必须停掉 | 假进程、协程、定时器不能漏到下一个测试。 |

## 验收标准

变更只有在下面每一项都交代清楚后，才能合并或发版。写明跑了什么、输出是什么。没跑的检查要列为没跑，不能省略。

1. **回退测试。** 把旧代码放回去跑新测试，必须真实失败并指出行为；再恢复变更，确认测试通过。
2. **在隔离环境里跑测试。** 用临时 HOME / 沙箱，不要碰本机真实配置。
3. **构建和完整测试套件。** 按项目自己的命令在目标平台上跑完整套件，不要只跑「以为改到的包」。
4. **跨平台复现。** 报告出在哪一端（macOS、Windows、Linux），就在那一端真实跑。只交叉编译不算测过。机器通过 SSH 操作，见 `scripts/repro-all.sh`。
5. **能真实使用就真实使用。** 改了哪家接入或哪条用户路径，就拿真账号、真配置、真界面去验。没实测过的功能，不许在上面接着开发，也不许跟用户说能用。
6. **把验证记录写进 commit 正文和 PR 评论。** 写明在哪个 head 上跑的。合并时使用 `gh pr merge --match-head-commit <已审 sha>`，审查期间如果又有 push，合并必须失败，未再审的代码进不来。

Draft PR 在标成 Ready 之前不能合。发版前，这次 tag 对应的 CI 必须跑完且全绿；被下一次 push 取消的跑次不算通过。

## 审查 PR

- 先把 head 拉下来，合到当前 `main` 上，再跑验收。只看 diff 不算审查。
- 故意把修复改坏，确认新测试能抓到。
- 平台报告要在对应机器上跑，GOOS 交叉编译不是测试。
- 预览、dry-run 不能有副作用。
- 文档和它链接的源码必须对得上。
- PR 只做它的目标。无关测试和重构另开。

## 提交

一条 commit 一个目标。标题写清改了哪一块、用户现在会看到什么，并带上 issue 或报告人。正文写怎么验证的，以及哪条测试在去掉该变更后会失败。验证记录放在 commit 正文里，不要只写在聊天或 PR 里。
